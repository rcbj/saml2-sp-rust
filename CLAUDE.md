# saml2-sp

Rust service provider for SAML 2.0 Web Browser SSO, plus a Shared Signals poll receiver. MIT. `develop` and `main` are one commit. A pull request merged into `main` publishes the crate to crates.io after the test workflow succeeds on that commit. A direct push does not. The token is the `CARGO_REGISTRY_TOKEN` repository secret. A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published.

## Usage

`ServiceProvider::from_file("saml.json", None, None)`, then `login` and `acs`. JSON keys match the Python configuration (`entityId`, `acsUrl`, `privateKey`, `certificate`, `idpMetadata`, bindings, `signals`, `ssf`). Exported names are `from_file`, `login`, `acs`, and `post_form_html`.

`signals` omitted or `true` keeps the receiver available and is omitted from the resolved configuration. `false` does not start a receiver and does not require transmitter metadata, and the resolved configuration includes `signals: false`. A non-boolean fails with `signals must be true or false`. The flag does not change the AuthnRequest: SAML does not send OAuth scopes.

Request bindings are `redirect` and `post`. Response bindings are `post`, `redirect`, and `artifact`. Artifact resolution is a signed SOAP `ArtifactResolve`. HTTP-Redirect query signatures use RSA-SHA256 (`http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`). Success is `urn:oasis:names:tc:SAML:2.0:status:Success`. `saml2-sp generate-keys` writes a self-signed RSA certificate.

## Tests

```bash
docker build --target test .
```

The `test` stage runs `cargo test`, then `cargo test --all-features` (the embedded PEP), in `rust:1`. GitHub Actions uses that command. Do not run Cargo on the host. The demo image does not run the suite.

Signatures and decryption are real. The stub identity provider signs with this crate's exclusive canonicalization and is created inside the tests.

`python3 scripts/live_iya_sts.py` signs the demo in to a fresh iya-sts (main, memory mode, no persistence, no clustering) and checks credential-change and session-revoked on `GET /live-status`. `IYA_STS_URL` uses a running iya-sts; `IYA_STS_IMAGE` starts one from an image; otherwise it clones and builds main. The registrar runs inside the demo image, never with Cargo on the host. Default ports 18518 (iya-sts) and 18618 (demo), `LIVE_STS_PORT` / `LIVE_DEMO_PORT`; it refuses 3000, 8081, and 18481 to 18495. The live script always starts a fresh iya-sts, but the install script may be run again against the same one (checked 2026-11-24): an existing registration has its metadata consumed again, and the other calls accept "already". Its order is install script, then demo image build, then run: it copies the checkout (no `demo/generated`, `.git`, `target`) to a scratch context, builds the image there once, runs the registrar in it (which writes the chain), builds again (only the `demo/` layer changes), checks the image's `demo/generated/idp-ca.pem` equals the saved file, and runs the demo with `sp.key`, `sp.crt` and `idp-metadata.xml` mounted file by file. It never fetches the CA for the demo, rewrites `idpCa`, or mounts a CA; it reads the saved chain only for its own HTTPS client. No script prints a password or secret, or a URL (trace lines carry fixed labels). Secrets reach `docker run` as `-e NAME`, the value in the child's environment. A generated test-user password goes to `demo/generated/<user>.password` (created 0600) and only that path is printed. Every `ssl` context in `scripts/` sets TLS 1.2 as the minimum. `--pep` (or `LIVE_PEP=1`, needs `IYA_STS_IMAGE` with #2026–#2028) sets the PEP up by running the install script with `--pep central` inside the demo image, copies the configuration to `demo/saml.pep-local.json` with `mode` `local` before the second build, checks the image's `demo/generated` holds only `idp-ca.pem`, and mounts `pep-key.pem` with the other files: central `GET /orders/42` 200 and `POST` 403, then (after the two events) local with `SAML_CONFIG=/app/demo/saml.pep-local.json`, the same two, and the application's OWN policy rewritten to deny `read` (`flip_policy`; never the realm root): the GET must be 403 within `PEP_FLIP_TIMEOUT` (30 s) with the PEP's `eventsReceived` up, so `via` is `event` (the fallback poll stays at 300 s). Against `iya-sts:live-2028-fga` (2026-11-24) both modes and the flip pass (1.1 s, by event). `.github/workflows/nightly.yml` runs the unit suite and that script at 07:10 UTC (`10 7 * * *`) and on `workflow_dispatch`. Push CI stays the unit suite.

## Embedded PEP

The embedded PEP (#40, iya-sts#1206 work item 8), behind the `pep` feature (`local` adds the engine), as `oidc-caep-risc` did in its #46: `src/pep.rs` wires in the shared `iya-pep` crate (rcbj/iya-pep-rust).
- `resolve_config` reads the `pep` section (`pep::section`): `signals` defaults to whether the receiver runs (an `ssf` block and not `signals: false`), `tlsCa` to `idpCa`, and a relative `assertionKey` is joined to the configuration's directory. Without the feature, a `pep` section is refused rather than ignored.
- `ServiceProvider::create`/`from_file` build and start it once the metadata is read: `pdpUrl` defaults to the identity provider's entityID (iya-sts's is the realm issuer, #523, realm prefix included) and `application` to `entityId`. It refuses an assertion key that is `privateKey` (the only key this library holds: signing, decryption, receiver TLS) by JWK thumbprint.
- `decide` / `decide_session` adapt a `SamlLogin` (`pep::subject_of`): the id is the `uid` OID, `uid`, or the AD FS `name` claim, else the NameID; attributes, `acr`, `amr`, `auth_time` as properties. `decide_session` takes the receiver's `MemorySessionIndex` (`SignalsReceiver::session_index`); an untracked or expired session is a Deny.
- `ReceiverOptions::pep`: `SignalsReceiver::new` adds `pep-policies-changed` to `events_requested` and registers the hand-over when the PEP wants events (`local`, or `central` with a Permit cache).
- `src/pep_test.rs` has its own stub PDP (on `support::serve`, which now records headers) and reuses `ssf_test.rs`'s transmitter. The no-feature refusal is in `sp_test.rs`. The `test` stage runs `cargo test` and then `cargo test --all-features`; the demo image builds with `--features local`.
- **The dependency is a git dependency on iya-pep-rust's `feature/1`** until that crate's first release. Switch it to the crates.io version then, because crates.io refuses a git dependency at publish.
- **The lock pins iya-pep `d88edef`** (feature/1): `mode` defaults to `local` (a build with `pep` alone refuses a section that leaves it out, so `pep_test.rs`'s sections name `central`, which they were written for; `a_section_without_a_mode_is_local` holds the default); the poll period follows the stream state; with signals on, a PEP starts as `EventStream::Down` until the receiver reports its stream.
- oidc-caep-risc's live run (its #46) found two defects; both are held here by `src/pep_test.rs`. `from_file` keeps the `pep` section (`from_file_keeps_the_pep_section`; this library's reader always did). ## Demo

`docker compose up --build`. `GET /healthz` is `200` with body `ok`. Pages: sign-in, `/login` (redirect or POST form), `/saml/acs`, and logout, plus metadata. Built with `pep` (the image uses `local`), `/orders/<id>` is decided by the PEP: 401 without a sign-in, 403 on a Deny, 503 when no decision could be made. `GET /live-status` is JSON `{signedIn, subject, receiver, events: [{type, jti}]}` (with a `pep` section, also `pep`: the PEP's status), never an assertion. The signed-in page has tabs **Session** (`/`, the old signed-in content) and **Policy enforcement** (`/?tab=pep`), as oidc-caep-risc's demo (its d5153d7, e2a7778): `pep_fragment()` draws `pep_json()` (the PEP's `Status`) as four `<details class="card pane" id="pep-…" open>` panes (Decisions, Cached policy, The PEP, Control plane), problems in `.problem`, everything escaped, or the "No embedded PEP" notice; `demo/public/pep.js` polls `GET /pep-status.html` every 2 s and keeps closed panes closed; `GET /pep-status` is the JSON. Both are 401 without a session. Pages carry `PAGE_CSP` (`connect-src 'self'` lets pep.js fetch). The demo's own tests (`src/bin/demo.rs` `mod tests`) hold the panes, escaping, counting, the notice, `human()` and the 401. When `session-revoked` matched no tracked session (the assertion SessionIndex was the assertion id), the demo ends its one local session and untracks it; that is demo code, not the library. Loopback entityID and assertion-consumer URLs follow `PORT`. Other hosts stay as written. `PUBLIC_URL` or `--public-url` replaces the origin and keeps the path. The default `http://localhost:3000` is not an explicit public URL. `demo/saml.json` uses `file:` placeholders and omits `signals`. Do not commit `demo/generated/`.

## Signals

With an `ssf` block and without `"signals": false`, the demo starts one poll receiver on the service provider's certificate (mutual TLS). `stop` waits for an in-flight poll. `scripts/configure_iya_sts.py` uses the `saml2-sp` binary on `PATH` (falling back to `cargo run`), registers the SP metadata, pins AES-256-GCM / RSA-OAEP, turns on multiple accounts, and, unless signals are off, grants `ssf.manage`. The container `PORT` wins over the shell `PORT` at registration.

## Trust chain (`idpCa`)

`idpCa` (default `file:generated/idp-ca.pem`, relative to `demo/`) is iya-sts's TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes it on every run through `scripts/trust_chain.py`'s `save_trust_chain()` (the copy the OIDC and GNAP repos carry; its CLI here reads `--config`/`SAML_CONFIG` and `--idp`/`IYA_STS_URL`): the whole chain from `GET /tls/server-certificate` (leaf, TLS Issuing CA, Intermediate, Root), falling back to the handshake's chain, and prints the path, the anchor's subject and SHA-256. It used to keep only the root from the handshake, and only when the file was missing. `src/http.rs`'s `trust_anchors()` adds every PEM block as a root: `native_tls::Certificate::from_pem` reads only the first (the leaf), and OpenSSL then fails with "self-signed certificate in certificate chain". The demo image carries the chain from build time: `.dockerignore` is `demo/generated/*` then `!demo/generated/idp-ca.pem`, and the demo stage's `COPY demo demo` (after `cargo build`, so a new chain does not rebuild the binaries) lands it at `/app/demo/generated/idp-ca.pem`. With no chain file the same COPY carries nothing from `demo/generated` and the build succeeds. Rebuild the image after re-running the install script against a different iya-sts. `src/trust_chain_test.rs` serves HTTPS from an rcgen four-certificate chain and checks the registrar writes all four (published and handshake) and that `ServiceProvider` fetches metadata trusting the file.

**Plain http (#12).** `http::send` is the one place every fetch goes through (metadata URL, `ArtifactResolve`, SSF configuration, JWKS, stream and poll). `refuse_plain_http_off_loopback` checks the URL ureq itself parsed (`Request::request_url`), before connecting and without resolving a name: plain `http://` to a host that is not loopback (`127.0.0.0/8`, `::1`, `localhost`) is refused, naming only the scheme and host[:port]; userinfo is never loopback. Redirects are followed by hand (`redirects(0)` and at most five hops, never https to http) so each hop gets the same check. A URL or `Location` holding whitespace or a control character is refused first (`refuse_whitespace_or_control`): the url crate drops tabs and newlines and trims spaces, so it could otherwise dial a host a reader does not see. No opt-out. `src/plain_http_test.rs` covers it; `http://0.0.0.0:<port>` reaches a 127.0.0.1 listener on Linux, so an empty backlog proves no connection was opened.
