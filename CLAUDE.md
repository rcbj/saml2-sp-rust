# saml2-sp

Rust service provider for SAML 2.0 Web Browser SSO, plus a Shared Signals poll receiver. MIT. `develop` and `main` are one commit. A pull request merged into `main` publishes the crate to crates.io after the test workflow succeeds on that commit. A direct push does not. The token is the `CARGO_REGISTRY_TOKEN` repository secret. A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published.

## Usage

`ServiceProvider::from_file("saml.json", None, None)`, then `login` and `acs`. JSON keys match the Python configuration (`entityId`, `acsUrl`, `privateKey`, `certificate`, `idpMetadata`, bindings, `signals`, `ssf`). Exported names are `from_file`, `login`, `acs`, and `post_form_html`.

`signals` omitted or `true` keeps the receiver available and is omitted from the resolved configuration. `false` does not start a receiver and does not require transmitter metadata, and the resolved configuration includes `signals: false`. A non-boolean fails with `signals must be true or false`. The flag does not change the AuthnRequest: SAML does not send OAuth scopes.

Request bindings are `redirect` and `post`. Response bindings are `post`, `redirect`, and `artifact`. Artifact resolution is a signed SOAP `ArtifactResolve`. HTTP-Redirect query signatures use RSA-SHA256 (`http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`). Success is `urn:oasis:names:tc:SAML:2.0:status:Success`. `saml2-sp generate-keys` writes a self-signed RSA certificate named `CN=<--cn, default "saml2-sp service provider">, O=saml2-sp` with the entityID (`--entity-id`, else the configuration's) as a subjectAltName URI (`service_provider_subject()`, `create_self_signed_key_pair_for()`; owner: never a bare host like the old `CN=localhost`); the install script passes `--cn "saml2-sp-rust demo SP"`.

## Signals

With an `ssf` block and without `"signals": false`, the demo starts one poll receiver, authenticated by mutual TLS with `Config::ssf_tls()`: `ssf.clientCertificate` / `ssf.clientKey` (both or neither; PEM, path relative to the configuration, or placeholder; must load as a `native_tls` identity, any key type) when given, else the SP key pair; `ssf_client_is_separate()`; the Session tab says which. `stop` waits for an in-flight poll. **Add/Remove Subject** (owner: by default an app receives events only about users with an active session there; iya-sts#2234): `track` queues Add Subject (`iss_sub` with the subject attribute and the transmitter's issuer, `email`; `verified: true`) and `untrack` / an event-ended session (`forget`, via `MemorySessionIndex::take`) queues Remove Subject per identifier no other session holds; `send_subject_calls()` runs at the top of `poll_now` (the poll thread, no new timer; nothing before the stream exists), once each, never retried: 403 is `warn` (the expected race), other failures `error`, latest in `subject_error()`; at most 1000 queued. Skipped without `add_subject_endpoint`/`remove_subject_endpoint`, with `ReceiverOptions::add_subjects` false (`ssf.addSubjects`, `ssf_add_subjects()`, default true) or signals off. Expiry sends nothing. ## Trust chain (`idpCa`)

`idpCa` (default `file:generated/idp-ca.pem`, relative to `demo/`) is iya-sts's TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes it on every run through `scripts/trust_chain.py`'s `save_trust_chain()` (the copy the OIDC and GNAP repos carry; its CLI here reads `--config`/`SAML_CONFIG` and `--idp`/`IYA_STS_URL`): the whole chain from `GET /tls/server-certificate` (leaf, TLS Issuing CA, Intermediate, Root), falling back to the handshake's chain, and prints the path, the anchor's subject and SHA-256. It used to keep only the root from the handshake, and only when the file was missing. `src/http.rs`'s `trust_anchors()` adds every PEM block as a root: `native_tls::Certificate::from_pem` reads only the first (the leaf), and OpenSSL then fails with "self-signed certificate in certificate chain". The demo image carries the chain from build time: `.dockerignore` is `demo/generated/*` then `!demo/generated/idp-ca.pem`, and the demo stage's `COPY demo demo` (after `cargo build`, so a new chain does not rebuild the binaries) lands it at `/app/demo/generated/idp-ca.pem`. With no chain file the same COPY carries nothing from `demo/generated` and the build succeeds. Rebuild the image after re-running the install script against a different iya-sts. `src/trust_chain_test.rs` serves HTTPS from an rcgen four-certificate chain and checks the registrar writes all four (published and handshake) and that `ServiceProvider` fetches metadata trusting the file.

**Plain http (#12).** `http::send` is the one place every fetch goes through (metadata URL, `ArtifactResolve`, SSF configuration, JWKS, stream and poll). `refuse_plain_http_off_loopback` checks the URL ureq itself parsed (`Request::request_url`), before connecting and without resolving a name: plain `http://` to a host that is not loopback (`127.0.0.0/8`, `::1`, `localhost`) is refused, naming only the scheme and host[:port]; userinfo is never loopback. Redirects are followed by hand (`redirects(0)` and at most five hops, never https to http) so each hop gets the same check. A URL or `Location` holding whitespace or a control character is refused first (`refuse_whitespace_or_control`): the url crate drops tabs and newlines and trims spaces, so it could otherwise dial a host a reader does not see. No opt-out. `src/plain_http_test.rs` covers it; `http://0.0.0.0:<port>` reaches a 127.0.0.1 listener on Linux, so an empty backlog proves no connection was opened.
